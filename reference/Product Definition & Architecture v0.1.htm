Product Definition & Architecture v0.1

1. Product Positioning

Produk ini adalah web-based photo booth system yang dapat digunakan melalui browser modern tanpa ketergantungan pada iPad atau aplikasi native tertentu. Tujuan utamanya adalah menyediakan pengalaman photo booth yang cukup profesional untuk event klien, tetapi tetap mudah diakses dari berbagai device seperti laptop Windows, MacBook, tablet Android, iPad, atau device lain yang memiliki browser dan kamera. Produk ini akan mengambil LumaBooth sebagai benchmark fungsional, tetapi desain, implementasi, arsitektur, dan positioning produknya dibuat sebagai sistem tersendiri.

Sistem ini akan bersifat free to use pada level penggunaan dasar, terutama untuk kebutuhan capture, layout, QR sharing, gallery sederhana, dan print manual. Untuk kebutuhan klien, sistem dapat dikonfigurasi per event sehingga setiap event memiliki pengaturan nama, layout, overlay, asset, dan mode output sendiri. Prinsip arsitektur utamanya adalah client-heavy processing, karena proses kamera, countdown, composition, overlay, dan export gambar sebaiknya dilakukan langsung di browser agar responsif dan tidak membebani server.

2. MVP Scope

MVP harus fokus pada core loop photo booth yang benar-benar dipakai saat event. Flow paling penting adalah user membuka event, sistem mengakses kamera, user melakukan capture dengan countdown, foto dikomposisikan ke layout dengan overlay, hasil akhir ditampilkan, user dapat retake atau menyimpan hasil, lalu hasil dapat dibagikan via QR, diunduh, masuk ke gallery, dan dicetak. Semua fitur di luar core loop dianggap sekunder sampai flow utama stabil.

Fitur yang masuk MVP adalah event setup, camera access, capture, countdown, layout composition, overlay, final output preview, QR download/share, simple gallery, dan printer integration. Event setup minimal harus bisa menentukan nama event, slug event, jenis layout, overlay aktif, countdown duration, jumlah foto dalam satu sesi, dan mode output. Gallery sederhana minimal harus bisa menampilkan hasil foto per event, membuka detail foto, menampilkan QR ulang, mengunduh ulang, dan menghapus item jika diperlukan.

Fitur yang tidak masuk MVP awal adalah AI background removal, beauty filter, stickers interaktif, virtual attendant, survey, email automation, WhatsApp gateway, payment gateway, dan advanced SaaS dashboard. Fitur tersebut bisa masuk roadmap berikutnya setelah MVP stabil di event nyata. Dengan cara ini, pengembangan tidak melebar ke fitur atraktif tetapi belum kritis, dan AI agent bisa diarahkan mengerjakan modul yang kecil, jelas, serta mudah diuji.

3. Primary User Flow

User flow utama dimulai dari admin atau operator yang membuat event melalui halaman setup. Admin mengisi nama event, memilih layout, mengunggah overlay PNG transparan, mengatur countdown, dan menyimpan konfigurasi. Setelah event dibuat, sistem menghasilkan event URL yang bisa dibuka pada device booth.

Tamu atau operator membuka halaman booth berdasarkan event URL. Browser meminta izin kamera, lalu sistem menampilkan live preview dengan tombol start. Setelah tombol start ditekan, countdown berjalan, foto diambil, lalu foto dikomposisikan dengan layout dan overlay menggunakan Canvas.

Setelah proses komposisi selesai, sistem menampilkan final output. User dapat memilih retake, download, share via QR, atau print. Hasil yang disetujui masuk ke gallery event agar bisa dilihat ulang selama event berlangsung.

4. Route Structure

Struktur route harus sederhana dan agent-friendly. Halaman utama dapat diarahkan ke landing sederhana atau redirect ke daftar event jika mode admin aktif. Route /setup digunakan untuk membuat dan mengatur event, sedangkan route /booth/[eventSlug] digunakan untuk pengalaman photo booth layar penuh.

Route /gallery/[eventSlug] digunakan untuk melihat hasil foto dalam event tertentu. Route /photo/[photoId] digunakan sebagai public share page yang dibuka ketika QR dipindai. Route /print/[photoId] dapat disediakan sebagai halaman print-optimized agar hasil cetak tidak terganggu elemen UI.

5. Core Modules

Modul event setup bertanggung jawab menyimpan konfigurasi event. Modul ini harus mendukung input nama event, slug, layout preset, overlay file, countdown duration, capture count, output format, dan printer mode. Pada MVP awal, konfigurasi dapat disimpan ke localStorage atau Supabase tergantung fase implementasi yang dipilih.

Modul camera access bertanggung jawab mengelola WebRTC MediaDevices API. Modul ini harus menangani permission request, fallback saat kamera gagal, camera switching jika device punya lebih dari satu kamera, serta cleanup stream saat halaman ditutup atau berpindah. Modul ini harus dipisah dari UI agar logic kamera bisa dites dan dipakai ulang.

Modul capture engine bertanggung jawab pada countdown, frame capture, dan state transition. Modul ini harus bisa menangani single photo terlebih dahulu, lalu dikembangkan ke multi-photo layout. Modul ini harus jelas membedakan state seperti idle, requesting camera, ready, counting down, capturing, processing, previewing, saving, dan error.

Modul composition engine bertanggung jawab pada penyusunan final output melalui Canvas. Modul ini harus menerima raw image, layout definition, overlay asset, dan output size, lalu menghasilkan Blob atau object URL. Komposisi harus dilakukan deterministic agar hasil preview dan hasil download atau print sama.

Modul sharing bertanggung jawab menghasilkan public URL dan QR code. Pada mode lokal, URL bisa mengarah ke object lokal atau data sementara, tetapi untuk mode event yang benar-benar dipakai klien, hasil perlu diunggah ke storage agar QR dapat dibuka di device lain. Modul ini juga harus mendukung download file langsung dari browser.

Modul gallery bertanggung jawab menyimpan daftar hasil per event. Untuk MVP lokal, gallery bisa berbasis IndexedDB agar tidak cepat memenuhi memory dan lebih tahan refresh. Untuk versi cloud, gallery membaca metadata dari database dan file dari storage.

Modul printer bertanggung jawab menyediakan print flow. Untuk semua device, sistem harus mendukung print standar melalui browser print dialog. Untuk booth station yang dikonfigurasi khusus, sistem dapat mendukung kiosk printing dengan Chrome atau Edge yang dijalankan menggunakan mode kiosk printing.

6. Architecture Decision

Arsitektur yang dipilih adalah hybrid edge-cloud. Client bertugas mengakses kamera, menjalankan countdown, mengambil frame, melakukan composition, menambahkan overlay, membuat preview, menghasilkan file output, dan menjalankan print flow. Server hanya bertugas menerima file final, menyimpan metadata, menyediakan public URL, dan melayani gallery atau share page.

Pendekatan ini dipilih karena photo booth sangat bergantung pada pengalaman real-time. Jika setiap capture harus dikirim ke server untuk diproses, latency akan naik dan risiko gagal saat koneksi buruk akan lebih besar. Dengan Canvas di client, pengalaman booth tetap cepat, sedangkan cloud hanya dipakai saat hasil akhir sudah siap dibagikan.

Untuk storage, MVP bisa dimulai dengan IndexedDB dan localStorage agar development cepat. Namun untuk kebutuhan klien, Supabase Storage dan PostgreSQL lebih cocok karena QR share harus bisa dibuka dari device lain. Jadi implementasi bisa dibuat bertahap dengan abstraction layer agar storage lokal dan cloud dapat diganti tanpa mengubah seluruh UI.

7. Suggested Tech Stack

Frontend utama menggunakan Next.js, React, TypeScript, dan Tailwind CSS. Next.js dipilih karena route structure jelas, deployment mudah ke Vercel, dan cocok untuk pengembangan berbasis agent. TypeScript wajib dipakai agar data model event, layout, photo, dan capture state tidak kacau ketika fitur bertambah.

Client media layer menggunakan WebRTC MediaDevices API untuk kamera dan HTML Canvas untuk composition. QR generation dapat menggunakan library ringan seperti qrcode atau react-qr-code. Penyimpanan lokal dapat memakai IndexedDB melalui wrapper seperti Dexie agar lebih rapi daripada memakai IndexedDB native secara langsung.

Backend awal menggunakan Next.js API routes atau server actions secara terbatas. Supabase digunakan untuk PostgreSQL, storage, dan public file URL. Deployment menggunakan Vercel karena sesuai dengan serverless flow dan mudah diintegrasikan dengan environment variable.

8. Data Model Awal

Entitas Event menyimpan konfigurasi event. Field minimalnya adalah id, name, slug, layoutId, overlayUrl, countdownSeconds, captureCount, outputWidth, outputHeight, printerMode, createdAt, dan updatedAt. Pada MVP lokal, entitas ini dapat disimpan di localStorage, tetapi bentuk datanya harus tetap dibuat seolah-olah siap masuk database.

Entitas Photo menyimpan hasil akhir setiap sesi. Field minimalnya adalah id, eventId, fileUrl, thumbnailUrl, width, height, createdAt, dan status. Jika upload belum selesai, status dapat bernilai local, uploading, uploaded, atau failed.

Entitas Layout menyimpan definisi posisi foto dan overlay. Field minimalnya adalah id, name, canvasWidth, canvasHeight, slots, dan backgroundColor. Setiap slot harus menyimpan x, y, width, height, fit, dan borderRadius agar composition engine bisa menggambar foto secara presisi.

9. Printer Strategy

Printer integration dibagi menjadi dua mode. Mode pertama adalah browser print mode, yaitu sistem membuka halaman print-optimized lalu memanggil print dialog menggunakan browser. Mode ini paling aman untuk semua device, tetapi tetap membutuhkan interaksi user atau operator karena browser tidak mengizinkan silent print universal.

Mode kedua adalah kiosk print mode. Mode ini ditujukan untuk device booth yang memang disiapkan khusus, misalnya laptop Windows dengan Chrome atau Edge dan default printer sudah dikonfigurasi. Pada mode ini, browser dapat dijalankan dengan flag kiosk printing sehingga proses cetak bisa jauh lebih seamless.

Mode ketiga adalah future local print bridge. Ini bukan MVP awal, tetapi dapat dibuat jika klien benar-benar membutuhkan integrasi printer yang lebih native. Bentuknya bisa berupa aplikasi kecil lokal yang menerima request dari web app melalui localhost, lalu mengirim file ke printer menggunakan kemampuan OS.

10. MVP Definition of Done

MVP dianggap selesai jika admin bisa membuat event sederhana dan membuka booth URL. Kamera harus bisa aktif, preview harus tampil stabil, countdown harus berjalan, capture harus menghasilkan gambar, dan composition harus menempelkan foto ke layout dengan overlay. Hasil akhir harus bisa ditampilkan, di-retake, diunduh, dibagikan melalui QR, masuk gallery, dan dicetak melalui browser print flow.

MVP juga harus stabil untuk penggunaan event pendek. Stream kamera harus dibersihkan saat tidak digunakan, object URL harus di-revoke setelah tidak diperlukan, dan state capture harus kembali bersih setelah sesi selesai. Error seperti kamera tidak diizinkan, kamera tidak ditemukan, upload gagal, dan print tidak tersedia harus ditampilkan dengan pesan yang bisa dipahami operator.

MVP tidak harus punya dashboard komersial lengkap. Namun struktur kode harus sudah memisahkan modul event, camera, capture, composition, sharing, gallery, dan print. Pemisahan ini penting agar iterasi berikutnya tidak berubah menjadi patchwork yang sulit dikendalikan.

11. First Development Milestone

Milestone pertama adalah membangun local-first prototype. Targetnya adalah membuat route setup, booth, gallery, dan print tanpa integrasi cloud terlebih dahulu. Semua data event dan hasil foto disimpan lokal agar core loop bisa diuji cepat.

Milestone ini harus menghasilkan UI yang sederhana tetapi fungsional. Fokusnya bukan visual final, melainkan flow yang benar, state yang bersih, dan composition yang akurat. Setelah core loop stabil, barulah cloud upload, public QR, dan gallery berbasis Supabase ditambahkan.

Output dari milestone pertama harus berupa aplikasi Next.js yang bisa dijalankan lokal, memiliki TypeScript types yang jelas, dan memiliki README setup. Agent juga harus membuat laporan perubahan, daftar file penting, asumsi teknis, known issues, dan rekomendasi task berikutnya. Dengan format ini, review bisa dilakukan secara objektif sebelum kita lanjut ke milestone kedua.
