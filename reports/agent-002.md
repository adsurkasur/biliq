## UX Improvements

The booth capture state now uses the full viewport with `dvh`, avoids page scrolling, centers a tablet portrait 3:4 viewfinder, and keeps only minimal operator controls visible. The start button is large and touch-friendly, while gallery/setup links are small and secondary.

The live viewfinder now layers video first, then the uploaded PNG overlay, then countdown/progress, then minimal controls. The overlay is stretched to the same output canvas dimensions used by final composition, so the live preview and generated output stay aligned as closely as possible.

The setup page now shows the selected output size, aspect ratio, recommended overlay PNG size, transparent PNG guidance, and a warning that mismatched overlay dimensions may not align perfectly. Uploaded overlay dimensions are read in the browser and shown with a match/mismatch status.

## Multi-Photo Implementation

Capture count is clamped to 1 through 4 and synced with layout presets:

- 1 photo: full-frame single layout.
- 2 photos: two vertical slots.
- 3 photos: three vertical strip slots.
- 4 photos: two-by-two grid layout.

When the operator chooses more than one photo, the guest presses start once. The booth runs the configured countdown before each shot, captures the video frame, updates progress such as `Photo 2 of 4`, and repeats until all frames are captured. Composition runs only after the final frame, producing one final image used by preview, save, download, gallery, QR detail, and print.

## Architecture Notes

Viewfinder preview remains in `components/CameraPreview.tsx`, while booth state and multi-shot sequencing live in `app/booth/[eventSlug]/BoothClient.tsx`. Layout definitions stay in `lib/layouts/defaultLayouts.ts`; canvas rendering stays in `lib/composition/composePhoto.ts`; frame capture stays in `lib/capture/captureFrame.ts`.

Event configuration still uses localStorage through `lib/storage/events.ts`. Saved photo records still use IndexedDB through `lib/storage/photos.ts`. QR values remain generated by `lib/qr/createQrValue.ts`, and print stays isolated to `/print/[photoId]` with browser print only.

## Known Limitations

QR links are still local-only and point to photo data in the same browser/device storage. Cross-device public QR sharing requires cloud upload later.

Printing remains browser-print only. Silent kiosk printing is intentionally not implemented; it requires device/browser setup such as Chrome or Edge kiosk printing mode.

The live viewfinder uses the same 3:4 output frame and cover behavior as the default single-photo composition. For multi-photo sessions, the live feed previews the current shot in the output frame, while the final composed output places captured frames into the selected slot layout.

Browser camera behavior depends on device support, permissions, and secure-context rules. Localhost works for development, but deployed camera use should be tested over HTTPS.
